# Platform P3.9 — Resumable Audit Verification

**Released as 2.4.1** (see §5 for why not 2.4.0), published to GitHub Packages, verified from a
clean install.

---

## 1. Verification Evolution Report — **Completed**

`verifyChain` initialised `previousHash = null` and the expected sequence to `null`, so a chain
could only be verified as a whole, from the record that chains from nothing.

Two additive changes:

```ts
export interface VerifyChainOptions {
  readonly formats?: CanonicalFormatRegistry | readonly CanonicalFormat[];
  readonly from?: ChainHead | null;   // ← new; absent or null means genesis
}
```

and a structured failure shape (§3).

**One routine, not two.** `from` decides only what the walk starts from. Everything after the
initialisation is the code that was already there, so an incremental pass and a whole-chain pass
check identically — which is what makes their answers comparable at all. A second "incremental
verifier" would have been two implementations of one guarantee, diverging silently.

**Scope held.** `verifyChain`, `VerifyChainOptions` and the result shape. Nothing else in the
package changed, and no product was touched.

## 2. Incremental Verification Report — **Completed**

### Why it was a capability gap and not a diagnostic one

Handing the verifier a continuation batch did not fail to detect a break. It **fabricated** one:
the batch's first record chains to a digest initialised to `null`, so the answer was
`valid: false, reason: 'previous hash does not match the preceding record', checked: 0` — on
completely intact evidence.

That result pages at the highest severity a compliance alert has. A verifier that raises it nightly
is worse than no verifier, because it trains an operator to ignore the one alarm that must never be
ignored. Munaxa Docs stopped its P4.7 migration on precisely this.

Separately, the expected sequence began at whatever the first record carried, so a record removed
from the **front** of a batch was invisible: every record present still chains to the one before it.

### Why the head is one field and not two

A resume point is a position *and* a digest, and supplying one without the other verifies half the
claim:

- Given only a hash, the front-of-batch removal above stays invisible.
- Given only a sequence, a forged leading record passes.

`ChainHead` already carries both, and it is already what `AuditSealer` receives on the append side.
Verification is the same problem from the other end and now has the same shape. A separate
`fromSequence` beside `fromHash` would have been two ways to describe one position, which is how
they come to disagree.

### Why absent and `null` are identical

A caller holding an optional checkpoint writes `from: checkpoint ?? null`. Had the explicit
spelling been stricter than the omitted one, a chain's **first-ever** pass would fail — the one run
where there is legitimately nothing to resume from, and the one nobody is watching for. Asserted
directly: `verifyChain(records, { from: null })` deep-equals `verifyChain(records)`.

### What the platform deliberately does not do

**It does not authenticate the head.** The platform cannot distinguish a head that came from a
signed checkpoint from one taken out of the first row of the batch being verified — and the latter
verifies the batch against itself, which proves nothing.

Signing the resume point stays the caller's, because the key must live where the platform has no
reach: not in the database holding the chain, and not in the bucket holding the export. An API that
appeared to authenticate it would claim a guarantee it cannot provide, which is worse than
declining to. This is the boundary `appendChained` already draws — the store owns ordering, the
platform owns hashing.

## 3. Structured Failure Report — **Completed**

| `code` | The accusation | Also carries |
|---|---|---|
| `SEQUENCE_GAP` | A record was removed and took its link with it — the hole a hash cannot see | `expectedSequence` |
| `LINK_MISMATCH` | A record was inserted or removed mid-chain, or the batch does not follow its head | `expectedPreviousHash`, `actualPreviousHash` |
| `DIGEST_MISMATCH` | A field was altered | `expectedHash`, `actualHash` |
| `UNKNOWN_FORMAT` | Sealed by a format this verifier was not given, so it has **not** been checked | — |
| `MISSING_IDENTIFIER` | The format needs an identifier the record does not carry | — |

Plus `brokenAtId` on every failure, beside the existing `brokenAt` position.

Three points worth stating:

- **The last two are not tamper reports.** An unverifiable record is not a broken one, and an alert
  that conflates them sends somebody looking for an intruder who was never there.
- **`expectedHash` is what the contents produce; `actualHash` is what the record claims.** That
  direction is deliberate — the contents are the evidence, not the store's assertion about them.
- **There is no `brokenSequence`.** The brief listed it, and it is the same number as `brokenAt`.
  Two names for one fact is how they come to disagree; `brokenAtId` was added instead because a
  position and an identifier answer genuinely different questions.

`reason` keeps its exact wording, so nothing that logs it changes. New code branches on `code`: a
prose string is not an API.

## 4. Consumer Compatibility Report — **Partially completed**, and honestly so

The brief asked for validation against three consumers. Only one of them has a chain to verify.

Docs can migrate its verification service with no workaround.

### Munaxa School — **not applicable**

Its `AuditLog` table has `id`, `action`, `entityType/entityId`, `before/after`, `metadata`,
`onBehalfOf`, `traceId`, `createdAt` — and **no `sequence` and no `hash`**. It is an append log, not
a tamper-evident chain, so there is no verification to resume. It consumes `@munaxa/ui`,
`@munaxa/theme`, `@munaxa/tokens`, `@munaxa/icons` and the config packages; it does not consume
`@munaxa/audit`, so this change cannot reach it.

If it adopts the chain, `from` is what its pass will need, for the same reason Docs did.

### Munaxa Work — **not applicable**

It has **no audit table at all** — only per-row audit *columns* (`created_by`, `updated_at`,
`deleted_by`, `version`), which is a different mechanism. Same package situation as School.

**Stated plainly:** this is one-consumer validation, not three. Claiming otherwise would be
describing a design review as an empirical result.

### The release incident, reported rather than buried

**2.4.0 is broken on the registry and cannot be installed.** Its tarballs carry unrewritten
`workspace:^` dependency ranges.

What happened: `pnpm publish -r` aborted on a 409 from `@munaxa/config-eslint@1.0.0` — an
unversioned package in the changesets `ignore` list — before reaching any platform package. I fell
back to a per-package loop using `npm publish`, which does not rewrite `workspace:` protocol
ranges. `pnpm publish` does. I knew this and used the wrong command anyway.

Caught by the clean-install verification, which is exactly what that step is for.

**2.4.1** is byte-identical in code, published with `pnpm publish`, and verified: dependency ranges
resolve to `^2.4.1`, a clean ESM install succeeds, and `require()` from CJS works.

GitHub Packages **does not support `npm deprecate`** — it returns `400 unmarshalling packument
failed` — so 2.4.0 cannot be marked as bad on the registry. The changelog entry is the only signal
available, and it says so explicitly. **Consumers must use 2.4.1 or later.**

## 7. Go / No-Go for Munaxa Docs P4.7 — **GO**

Everything P4.7 stopped on is closed:

| P4.7 blocker | Status in 2.4.1 |
|---|---|
| No way to express a resume point | `VerifyChainOptions.from` |
| A sound continuation batch reported as broken | Verifies correctly — validated on the published package |
| Front-of-batch removal invisible | `SEQUENCE_GAP` with `expectedSequence` |
| `BreakReason` flattened to prose | `code` maps 1:1 onto `DIGEST_MISMATCH` / `LINK_MISMATCH` / `SEQUENCE_GAP` |
| `expectedHash` / `actualHash` absent | Present on `DIGEST_MISMATCH` |
| `brokenAt` was a sequence, not the record id | `brokenAtId` added |

Two things P4.7 should carry into its plan:

1. **Two codes are new to that product.** `UNKNOWN_FORMAT` and `MISSING_IDENTIFIER` have no
   `BreakReason` equivalent, because the local verifier has no format registry. They must be handled
   explicitly and must **not** be reported as tampering — an unverifiable record is not a broken one.
2. **Delete `platform-verification-gap.spec.ts`.** It was written to fail once the platform gained a
   starting head. Its job is done.

Bump to `^2.4.1` — **not** `^2.4.0`.

## The lesson, recorded

`verifyChain` was designed for the shape the platform verifies: a whole chain, in memory, from
genesis. A consumer whose chain is millions of rows and verified nightly in batches from a signed
resume point was never in view.

The append side already knew it did not own ordering — that is exactly why `appendChained` hands
the adapter the head and takes a sealer back. Verification is the same problem from the other end
and did not get the same treatment.

P4.6 recorded that a consumer survey should look at **defaults**, not only names and types. This
phase adds the more general form: **survey a consumer for how a capability is _operated_, not only
for what it computes.** Five consecutive releases have now been unblocked by something a consumer
found afterwards; each one was visible in the consumer's code before the platform's was written.
