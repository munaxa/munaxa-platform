## 1. P-1 — Audit framework evolution

### What was wrong

Three separate constraints, each fatal on its own for a product with a live audit table:

- `AuditRecord.sequence` was a `number`. A table running for years on a `bigserial` cannot represent
  its sequence in a double past 2^53 — and silently losing precision on the column that proves
  nothing was removed from the end of the chain is not a trade worth making.
- `canonicalize` was a frozen function. The format could never change, because changing it would
  invalidate every digest ever written.
- `appendChained` opened its own transaction. An audit record that commits beside a business
  transaction that then rolls back is evidence of something that never happened.

### What changed

**`AuditSequence = number | bigint`**, with `sameSequence`, `nextSequence` and `compareSequences`
replacing `===`, `+ 1` and subtraction — all three of which are wrong across the two representations
(`1 === 1n` is false; `1n + 1` throws; `bigint - bigint` cannot drive `Array.sort`). Format 1 renders
the sequence as bare decimal digits rather than through `JSON.stringify`, which throws on a bigint —
so `canonicalize(…, 7)` and `canonicalize(…, 7n)` produce **identical bytes**, and a column migrated
from `int` to `bigint` needs no re-sealing.

**Versioned, pluggable canonical formats.** `CanonicalFormat` is a value with a `version`;
`CanonicalFormatRegistry` holds the set a verifier accepts; `verifyChain` re-hashes each record with
the format that sealed *it*. A chain spanning a format change verifies end to end in one pass.

Two decisions worth defending:

- **Absent `formatVersion` means format 1**, and the platform still omits the field when sealing with
  format 1. An append-only audit table cannot be back-filled, so the format has to be discoverable
  from the row rather than assumed by the verifier — and every 2.0.0 record stays byte-identical.
- **An unknown format fails verification rather than being skipped.** A verifier that cannot check a
  record has not established that it is intact, and reporting "valid" for a chain it only partly read
  is precisely the false assurance the chain exists to prevent.

**Transactional appends.** `appendChained(tenantId, seal, { transaction })`. The handle is `unknown`
so the platform depends on no database client; an adapter that does not recognise it must **throw**
rather than quietly opening its own — that silent fallback is the failure being prevented, not a
convenience. `joinsTransactions` advertises support, absent meaning false, which keeps every 2.0.0
adapter correct. A chain conflict inside a joined transaction is **not** retried: that transaction is
already aborted, so a retry within it cannot commit.

Costs are documented rather than hidden: the head read and insert move inside the caller's
transaction, so chain contention becomes the caller's contention.

### Collateral, found while doing it

`JSON.stringify` throws on a bigint, so every exporter and the logging sink would have failed on a
bigint-sequenced chain. Both now render one as decimal digits — which is also exact past 2^53, where
a JSON number is not. Number sequences are untouched, so existing exports and log lines are
byte-identical.

### Proof

14 new tests in `@munaxa/audit`, including: identical digests across representations; a sequence past
2^53 rendered exactly; a bigint chain verifying and its gap still detected; a chain spanning a format
change verifying; tampering still detected in a record sealed by the later format; an unknown format
refused; a transaction handle forwarded; a store that cannot join one refusing; and no retry inside a
joined transaction. The pre-existing `compat.test.ts`, which pins the 1.0 canonical bytes, passes
unchanged — which is the assertion that matters most here.

## 2. P-4 — Configuration framework evolution

### What was wrong

`@munaxa/config` was unadoptable by any product with existing deployments, for three independent
reasons:

- `PLATFORM_SCHEMA` hard-codes `MUNAXA_*`. Adopting it renamed every variable in every deployment —
  Helm values, App Service settings, `.env`, CI secrets — simultaneously.
- The resolved record is flat; products read nested config objects.
- `FieldDefinition` parses one variable and cannot express a rule spanning two.

### What changed

**Aliases.** `string({ env: ['DATABASE_URL', 'POSTGRES_URL'] })` per field, and `remapSchema` to add
them to a schema the product does not own — the usual case, since `PLATFORM_SCHEMA` is the
platform's. Remapping rather than forking is deliberate: a fork stops receiving fields the platform
adds later. Semantics chosen for a real rollout: the canonical name wins when both are set (so a
rename actually completes), an empty value falls through (a Helm value rendering to `FOO=` is not
set), and errors name the variable that held the bad value while never printing the value.

`remapSchema` refuses an unknown field name. A typo would otherwise be invisible — the field keeps
its original name and the deployment fails on a variable the operator believes they set.

**Nested output.** Fields carry a dotted `path`; `nestConfig` renders the shape. Additive — the flat
record is unchanged and both are available, so no call site changes in the same commit as the schema
swap. Prototype-polluting segments and conflicting paths are refused rather than silently producing a
config object missing a value.

**Schema-level refinement.** `defineConfig(fields, { refine })`. Issues join the field issues in one
message, so a deployment still learns everything in one restart. Refinements do **not** run when a
field failed to parse: a rule reading a value that never parsed reports a second, misleading problem
for the same cause.

**Extension schemas.** `extendConfig(PLATFORM_SCHEMA, productFields)`. Redefining a platform field is
refused — a product overriding the platform's definition of a session timeout or password policy is
how a security setting quietly stops meaning what the platform documents. Base refinements survive
extension: extending is not a way to drop the platform's rules.

### Proof

21 new tests in `@munaxa/config`. Backward compatibility is explicitly pinned: `parseConfig` and
`redactConfig` still accept a bare field map, and `PLATFORM_SCHEMA` parsing is unchanged.

## 3. P-5 — Session framework evolution

### What was wrong

The platform served exactly one architecture. `@munaxa/session` needs a `SessionStorePort`, and a
product whose only server-side auth object is a refresh-token lineage — self-contained short-lived
access token, one row per family, tokens rotating within it — had to add a table and rewrite its
refresh flow to supply one. That is a product change wearing a migration's clothes, which is why the
first consumer correctly refused to do it under a migration phase's rules.

### What changed

**`RefreshFamily` and `RefreshFamilyStorePort`** state the second architecture in the platform's own
vocabulary: the same lifecycle fields, keyed by family, with the same atomicity notes — including an
optional `createWithinLimit`.

**`sessionStoreOverFamilies`** presents one as the other, so `SessionManager` runs unchanged over
either. The mapping is an identifier re-brand and nothing else; a round-trip test pins it, because a
dropped or defaulted field would mean the two paths silently diverge in lifecycle behaviour.

**Optional capabilities are forwarded only when present.** Defining `createWithinLimit`
unconditionally would make `SessionManager` report `store-transaction` enforcement for a store that
cannot provide it — a limit that is a hint, described as a limit. This is the same requirement the
previous phase insisted on, held at the adapter layer.

**`MemoryRefreshFamilyStore`** implements a genuinely atomic `createWithinLimit`: count, evict and
insert with no `await` between them. A yield point there is exactly the gap two parallel sign-ins slip
through, and the resulting overshoot is invisible to any sequential test.

### Proof

The **existing session conformance suite runs a second time** against the family-backed store, so
"identical semantics" is checkable rather than asserted in a guide — concurrency cases included,
since the family store enforces in-store (conformance: 87 → 94 tests). Plus 8 targeted tests: create,
validate and revoke with no sessions table; `limitEnforcement === 'store-transaction'`;
`best-effort` correctly reported for a store without the capability; and a 12-way parallel sign-in
burst held to a limit of 2.

### What a product still has to do

Add the columns. `lastSeenAt`, `idleExpiresAt`, `absoluteExpiresAt`, `authMethods`, `mfaSatisfied`
and `tokenVersion` are usually new on a family table — and the two deadlines are the substantive
addition, because a refresh lineage with no absolute deadline lives as long as a thief keeps rotating
it. That is a product schema change, correctly scheduled as one, not a hidden platform workaround.

## 4. Backward compatibility

Every change is additive. Specifically:

| Surface | State |
| --- | --- |
| Format 1 canonical bytes | unchanged, pinned by `compat.test.ts` |
| `canonicalize(event, previousHash, recordedAt, sequence)` | still exported, still format 1 |
| `verifyChain(records)` with no options | still verifies a format-1 chain |
| `AuditRepositoryPort` implementations from 2.0.0 | still compile, still pass conformance |
| `parseConfig` / `redactConfig` with a bare field map | unchanged |
| `PLATFORM_SCHEMA` parsing | unchanged |
| `SessionStorePort`, `SessionManager` | unchanged |

One widening worth naming: `ChainConflictError.attemptedSequence` is now `AuditSequence` rather than
`number`. Constructing one with a number still compiles; reading one into a `number` variable no
longer does. It is a `minor`, not a `major`, because the only code that reads that field is code that
already handles the chain, and the alternative — a bigint chain reporting conflicts at rounded
positions — is worse than a type error.

**No breaking change was required.** Nothing needs a major version.

## 8. Go / No-Go — resuming the Munaxa Docs migration

**Go.**

Every gap that stopped the first migration is closed, each is proven by tests rather than asserted,
and nothing a consumer already depends on changed. The three product phases that were blocked can
resume in any order.

Two things the next phase should carry forward:

- **P4.3 sessions is unblocked, not free.** The family model still needs the deadline and decision
  columns on the product's family table. Schedule it as an explicit product change with schema
  authority — which was the first migration's own recommendation, and it was right.
- **Run the integration suite after every step.** It has already caught one defect the unit tests
  were structurally incapable of finding.
